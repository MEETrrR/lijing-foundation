# 考研决策工作台与计划自律联动设计

**版本：** v1.0
**日期：** 2026-09-03
**状态：** 已获用户确认，已进入实施计划
**适用范围：** 砺境考研目标选择、目标评估、院校专业推荐、学习计划与提醒自律联动

## 1. 目标

为砺境建立一条可持续使用的考研决策与执行闭环：

1. 用户有明确目标时，先搜索并选择自己想考的院校和专业。
2. 用户不确定时，再通过画像问答获得多档院校专业推荐。
3. 目标确定后，系统基于可追溯的数据生成目标评估、风险说明和下一步补强建议。
4. 用户确认目标后，可选择系统自动规划、混合规划或完全手动记录每日自律。
5. 已确认的计划可以写入现有计划、提醒和自律模块，形成目标、任务、提醒、完成记录和复盘的连续链路。
6. 院校、分数线、招生、费用、就业方向和薪资等信息都带有数据年份、来源、版本和更新时间，不把推断包装成事实或录取保证。

第一版先实现考研场景，但数据、规则和计划接口要能够复用于后续的职业选择、考公岗位和其他升学决策。

## 2. 非目标

- 第一版不承诺接入完整实时数据；先使用明确标注的演示数据适配器，并保留官方数据和市场数据适配边界。
- 不输出“录取概率 87%”一类容易误导的确定性概率，也不承诺录取、毕业薪资或就业结果。
- 不允许客户端或 AI 直接写入最终评估、计划完成、进度、提醒发送结果等服务端事实。
- 不让客户端或业务模块直接调用模型供应商、数据库、队列或私有对象存储。
- 不在本次实现中覆盖职业、考公和完整实时爬取系统；只保留可复用的决策和证据结构。
- 不自动替用户更换目标、删除手动任务或悄悄重排已确认计划。
- 不把缺少可靠来源的指标填成看似精确的数字。

## 3. 用户流程

### 3.1 已有目标

1. 用户进入考研决策工作台，选择“我已有目标”。
2. 搜索或筛选院校、专业和地区，打开院校专业详情。
3. 用户填写或确认本科专业、当前成绩基础、英语/数学基础、目标地区、预算、是否跨考、预计考试时间和目标方向。
4. 系统先执行报考条件和数据完整性检查，再生成目标评估。
5. 评估以“冲刺、匹配、稳妥”呈现，不使用录取概率；每一项结论都展示证据、差距、风险和数据更新时间。
6. 用户可以保存目标、加入对比，或直接进入计划草稿。

### 3.2 还不确定

1. 用户选择“我还不确定”。
2. 系统通过 6 到 8 个问题收集最小必要画像：本科背景、兴趣方向、基础、地区偏好、预算、跨考意愿、可投入时间和期望发展方向。
3. 推荐引擎先按硬性条件筛选，再输出 3 到 5 组院校专业组合。
4. 结果按冲刺、匹配、稳妥分组，允许用户修改地区、预算、跨考、难度和发展方向后重新计算。
5. 每个推荐必须说明“为什么推荐、主要匹配点、最大风险、需要补强什么、使用了哪些数据”。
6. 用户可以把推荐项转为目标，也可以返回继续填写自己的目标。

### 3.3 目标确认后的执行

1. 用户确认目标后选择自动规划、混合规划或自己安排。
2. 自动规划先生成草稿，展示假设条件，例如考试日期、距离考试天数、每日可用时长、阶段划分和科目投入比例。
3. 用户确认草稿后，系统通过 Planning 模块接口写入计划，再通过 Notification 模块创建提醒意图。
4. 混合规划允许用户接受阶段目标并逐日调整；手动模式不生成系统任务，只记录用户主动填写的每日自律。
5. 完成、延期和取消由用户提交，服务端记录事实。连续未完成只触发复盘建议，不擅自修改目标。

## 4. 页面与交互结构

### 4.1 考研决策首页

- 当前保存的目标院校专业。
- 当前计划完成度和今日任务。
- 最近一次数据变化和数据更新时间。
- 两个主入口：“我已有目标”和“我还不确定”。

### 4.2 目标选择页

- 院校、专业、地区搜索。
- 学科门类、考试科目、学费、学制和难度筛选。
- 关键事实摘要、数据年份、来源类型和更新时间。
- 加入对比和保存目标。

### 4.3 目标评估页

- 顶部显示冲刺、匹配或稳妥等级。
- 分数差距、报考条件、竞争程度、成本和发展方向分区展示。
- 主要依据、主要风险和下一步补强。
- 明确区分官方事实、市场样本和系统推断。

### 4.4 不确定推荐页

- 分步画像问答，允许返回修改。
- 推荐结果按三档展示，不突出单一“唯一正确答案”。
- 条件调整后重新计算，并显示新的规则版本和数据快照。

### 4.5 计划与自律页

- 目标、阶段、今日任务、提醒状态和复盘入口集中展示。
- 自动、混合、手动三种模式可切换。
- 支持单日调整，不要求用户重做整个计划。
- 手动任务和系统任务使用同一套完成记录接口，但保留来源类型。

### 4.6 数据追踪页

- 查看分数线、招生、费用、就业方向和薪资样本的变化。
- 每条变化显示变化时间、数据年份、来源、影响范围和是否需要重新评估。
- 数据刷新先产生变化记录，不直接改写历史评估结论。

视觉沿用砺境已有的深墨蓝、岩灰、琥珀金和少量朱砂红。星陨砺境的世界观用于陪伴感和识别感，但不遮挡分数、来源、风险和计划等决策信息。

## 5. 模块边界与所有权

本功能新增一个面向用户决策的 `Postgraduate Decision` 模块，并扩展教育数据能力。模块只通过接口、投影或版本化事件协作，不能写入其他模块的事实表。

| 模块 | 负责内容 | 允许的依赖 | 不得写入 |
|---|---|---|---|
| User Profile | 用户画像、偏好、目标方向、同意状态 | Identity、平台安全 | 身份凭据、学习结果、院校源事实 |
| Postgraduate Decision | 已选目标、对比项、评估快照、推荐快照、决策状态 | User Profile、Education Data、Planning、Analytics & Evidence、AI Gateway | 计划完成事实、提醒投递事实、教育源数据 |
| Education Data | 院校专业目录、考试科目、分数线、招生、费用、就业和薪资指标、来源与版本 | 平台、受控数据适配器 | 用户画像、推荐结论、计划事实 |
| Planning | 计划、阶段、任务、计划修订和用户提交的完成事实 | User Profile、Postgraduate Decision 的目标投影 | 教育源数据、评估结论、提醒投递结果 |
| Notification | 提醒意图、偏好约束、投递状态和频率控制 | User Profile、Planning | 学习完成事实、目标评估 |
| Analytics & Evidence | 只读变化投影、指标版本、证据导出 | 各领域事件和已批准数据 | 任一模块的源事实 |
| AI Gateway | 结构化结论的解释、追问和语言化呈现 | Identity、Policy & Configuration、Trust & Safety | 教育事实、评估分数、计划完成、供应商凭据 |

用户画像、计划行为和 AI 请求元数据按现有数据分类默认为 L2，日志只记录 ID、版本、状态、耗时和原因码，不记录完整问答、完整模型输入输出或敏感个人内容。

## 6. 核心数据结构

以下是对外行为所需的概念结构，不是数据库表定义：

### 6.1 教育数据事实

- `program_id`：稳定的院校专业标识。
- 院校、专业、地区、学科门类、考试科目、学制、费用和报考条件。
- 分数线、招生规模、复试比例等指标及其统计年份。
- 就业方向、薪资区间和样本范围；没有可靠数据时为空并附原因。
- `source_type`：`official`、`market_sample`、`inferred` 或 `demo`；`demo` 只能用于明确标注的合成数据。
- `source_reference`、`data_year`、`observed_at`、`updated_at`、`data_snapshot_id`。

### 6.2 用户考研画像

- 本科专业和背景。
- 英语、数学及专业课基础的用户自评或测评结果。
- 目标地区、预算、是否接受跨考、可投入时间和发展方向。
- 预计考试时间、当前成绩或估算分数。
- 用户对每项信息的确认时间和信息完整度。

### 6.3 决策结果

- 目标选择或推荐选择的 `program_id`。
- `decision_level`：`reach`、`match`、`safer`，对用户显示为冲刺、匹配、稳妥。
- 硬性条件检查结果。
- 匹配维度、差距、风险、补强建议和证据引用。
- `rule_version`、`data_snapshot_id`、`generated_at`。
- 评估快照不可被刷新操作原地改写；新数据产生新快照。

### 6.4 计划草稿与计划连接

- 目标、考试日期、阶段、科目、每日可用时长和薄弱项。
- `plan_mode`：`auto`、`hybrid` 或 `manual`。
- 阶段目标、周任务、日任务、预计时长和提醒偏好。
- 草稿状态：`draft`、`confirmed`、`rejected`、`superseded`。
- 确认后产生对 Planning 模块的写入请求和关联 ID；手动模式仍可记录每日自律，但不产生系统生成任务。

## 7. API 与写入规则

第一版使用 `/api/v1`，不暴露数据库表、SQL、内部队列或模型提供商信息。代表性接口如下：

| 方法 | 路径 | 用途 | 类型 |
|---|---|---|---|
| GET | `/api/v1/postgraduate/programs` | 搜索和筛选院校专业 | 读 |
| GET | `/api/v1/postgraduate/programs/{program_id}` | 读取院校专业详情和证据 | 读 |
| GET/PUT | `/api/v1/me/postgraduate/profile` | 读取或保存考研画像 | 读/写 |
| POST | `/api/v1/me/postgraduate/targets` | 保存用户选择的目标 | 写 |
| POST | `/api/v1/me/postgraduate/recommendations` | 根据画像生成推荐快照 | 写 |
| GET | `/api/v1/me/postgraduate/targets/{target_id}/assessment` | 读取目标评估快照 | 读 |
| POST | `/api/v1/me/postgraduate/targets/{target_id}/plan-drafts` | 生成计划草稿 | 写 |
| POST | `/api/v1/me/postgraduate/plan-drafts/{draft_id}/confirm` | 确认计划并连接 Planning/Notification | 写 |
| GET | `/api/v1/me/postgraduate/updates` | 读取保存目标的数据变化 | 读 |

所有写操作都要求 `request_id` 和 `Idempotency-Key`，并绑定认证用户、路由和规范化请求指纹。重复请求返回原结果；同一键复用不同载荷返回冲突。客户端只能提交选择、偏好、任务意图和完成意图，不能提交评估等级、分数差距、计划完成度、提醒已发送或任何最终结果。

计划确认是一个跨模块用例：Postgraduate Decision 先保存确认意图和关联快照，再通过 Planning 的应用接口创建计划；提醒通过 Notification 的应用接口创建，不直接写其他模块的存储。失败时保留可重试状态，不能把半成功显示成已完成。

## 8. 推荐与评估规则

### 8.1 已有目标

1. 执行硬性条件检查：学历、专业限制、考试科目或其他公开报考要求。
2. 对学术背景、初试准备度、考试科目匹配、地区与发展方向、成本和竞争程度进行可解释评分。
3. 使用固定且版本化的规则配置输出冲刺、匹配或稳妥等级。
4. 输出影响最大的匹配点和风险点，而不是单一总分。
5. 任何事实性数字必须引用 Education Data 的数据快照；推断结果标记为 `inferred`。

### 8.2 用户不确定时

1. 先按不可接受条件筛选，避免把用户明确排除的地区、预算或跨考范围重新推荐。
2. 对剩余候选按匹配度、准备成本、竞争风险和发展方向进行排序。
3. 使用多样性约束，避免 3 到 5 个结果只是同一院校或同一难度的重复项。
4. 每个结果必须能生成结构化解释；解释缺少证据时降级为模板或标记数据不足。

规则版本和数据快照一起保存。数据更新后可以提示重新评估，但不会删除或覆盖历史结论。推荐引擎没有候选时返回原因和可调整条件，不返回编造的替代院校。

## 9. 计划生成与自律联动

自动计划根据目标专业的考试科目、考试日期、用户基础、薄弱项、每日可用时长和休息约束生成阶段、周和日任务。默认阶段为基础、强化、冲刺和复盘，但阶段日期应由考试日期和可用时间计算，不写死具体年份。

计划生成只产生草稿，草稿中明确显示假设。用户确认后才写入 Planning；用户拒绝或修改后可以重新生成新草稿，旧草稿保留状态。

- `auto`：系统生成阶段、周和日任务，用户确认后执行。
- `hybrid`：系统生成阶段和周目标，用户可以逐日调整；手动修改优先级高于系统建议。
- `manual`：用户自己填写每日任务和时长，系统只负责记录、提醒和复盘统计。

提醒只创建“提醒意图”，最终投递状态由 Notification 模块负责。系统遵守学习时段、免打扰时间和提醒频率。用户手动标记完成、延期或取消后，系统记录事实并在周复盘中提供调整建议，不擅自降低目标或制造完成记录。

## 10. AI 使用边界与降级

AI Gateway 可提供以下能力：

- 将结构化评估解释成用户易懂的语言。
- 针对用户已提供的条件追问缺失信息。
- 将结构化计划草稿解释为可执行建议。

AI 输入只包含已授权的结构化画像、评估和证据引用；AI 输出必须通过 schema 校验，不能新增未引用的学校、分数、薪资或就业率。AI 不可用、被限流或被策略拒绝时，页面使用规则引擎和模板继续工作，并明确显示降级状态。

## 11. 错误处理与数据更新

- 画像信息不足：指出缺少哪些字段，并允许先保存草稿。
- 目标不存在或已下线：不泄露内部原因，提示重新搜索或选择其他目标。
- 没有匹配候选：展示触发冲突的条件，并允许逐项放宽。
- 数据过期：显示数据截至日期和过期标记；不伪装成实时数据。
- 数据源暂时不可用：使用最近已验证快照或返回“暂不可评估”，不生成新的未经证实数字。
- 计划与已有计划冲突：返回冲突项，允许用户调整时间或选择不写入。
- 提醒权限关闭：计划仍可保存，提醒状态显示为未启用，不把创建意图当成已发送。
- AI 失败：回退到模板解释，保留规则结果和证据。

数据刷新生成新 `data_snapshot_id` 和变化记录。变化记录包含旧值、新值、统计范围、来源和影响的目标；历史评估仍引用旧快照，用户主动确认后才生成新评估。

## 12. 测试与验收

### 12.1 单元与契约测试

- 院校专业筛选、硬性条件、评分维度和三档等级的边界测试。
- 推荐结果必须包含理由、风险、补强项、规则版本和数据快照。
- 缺失来源或过期数据不会生成伪造数字。
- 计划阶段、日期、任务时长和三种计划模式的确定性测试。
- OpenAPI 契约、事件 envelope、错误响应和写入元数据测试。

### 12.2 集成与安全测试

- 目标、画像、推荐和计划确认的幂等重试与冲突测试。
- 客户端提交伪造评估等级、完成度、提醒状态或薪资结果时被拒绝。
- 计划确认只通过 Planning/Notification 应用接口完成，不跨模块写入。
- AI 不可用时模板降级仍返回可用结果。
- 数据刷新保留历史快照且变化可追溯。
- 日志和错误响应不包含完整画像、完整 AI 内容、凭据或私有 URL。

### 12.3 用户界面验收

- 桌面和移动端页面无横向溢出，目标、证据、风险和任务文本不互相遮挡。
- 键盘操作、焦点状态、表单错误、空状态、加载状态和减少动画偏好可用。
- 真实用户流程覆盖“已有目标”和“不确定推荐”两条入口，以及自动、混合、手动三种计划模式。
- 数据源类型、数据年份、更新时间和演示数据状态在关键页面可见。

验收完成的最低条件是：用户可以选择目标或获得推荐，生成并确认计划，计划能进入提醒/自律链路，所有结果可追溯，数据和 AI 不可用时系统仍能诚实降级。

## 13. 分阶段交付

1. **决策底座**：教育数据模型与演示适配器、画像、目标选择、评估规则和契约。
2. **不确定推荐**：画像问答、推荐快照、对比和条件调整。
3. **计划联动**：自动/混合/手动计划、Planning/Notification 接口和自律记录。
4. **持续追踪**：数据快照刷新、变化记录、重新评估提示和证据展示。
5. **真实数据接入**：在来源、授权、口径、更新频率和合规审查明确后替换适配器。

职业、考公和其他升学场景后续复用决策快照、证据版本、计划确认和自律联动机制，只新增各场景自己的事实模型和规则，不把考研页面复制成多个孤立系统。
