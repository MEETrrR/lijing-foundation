# 砺境前端审查：从字体到框架

**日期：** 2026-10-18
**范围：** `apps/user_client`（原生 Web Modules，无构建步骤，源码直出）与 `assets/generated`
**方法：** 全部结论来自脚本实测，不取印象。工具在 `_ljing_audit/`：CSS 解析器、对比度计算、
几何回归探针（CDP 逐元素前后对比）、多视口截图、资源体积普查、字体 cmap 校验。
**限制：** 应用主体在登录墙后，本地用桩住 `/api/v1` 的 harness 渲染；`/admin`、`/map`、
`/cet`、`/route` 的表单态未逐一目检。未做键盘与读屏审计，未测真实网络下的 LCP/CLS。

---

## 1. 结论摘要

按影响从大到小，只有三条真正重要：

1. **资源层是全站最大的问题，而且已经解决了一半。** 仓库带 54 个图片/视频共
   **114.8 MB**，其中 **41 个从未被任何代码引用（84.1 MB）**；被引用的 10 张图全是 PNG，
   合计 27.1 MB。但仓库里**已经存在**这些图优化好的、带内容哈希的 WebP 版本，
   只是 11 个里只有 1 个接进了 `assets.js`。把接线补上之后，首页首次传输从
   **3,585 KB 降到 759.6 KB（-79%）**，底图单张从 2,887 KB 降到 61 KB。

2. **品牌字形此前完全由访客的操作系统决定。** `document.fonts.size = 0`，全站零 `@font-face`：
   Windows 走楷体、macOS 走 STKaiti、Android 与 Linux 没有中文衬线，整站「水墨/东方」气质
   直接塌成无衬线。已自托管按站点实际字符集子集化的霞鹜文楷（993 码位，197 KB woff2）。

3. **排印和间距此前没有刻度。** 51 个字号档位（正文只有 8–11px，128 个文字色里 69 个
   alpha < .55，深底上不足 4.5:1）、71 个间距取值。已收敛为 10 个字号令牌 + 12 档间距，
   全部文字达到 4.5:1。

## 2. 逐层发现

### 2.1 资源层（已部分修复）

| 项目 | 实测 |
|---|---|
| 资源总数 | 54 个（png 41 / webp 11 / mp4 1 / svg 若干） |
| 总体积 | 114.8 MB |
| 被引用 | 13 个，30.6 MB |
| **从未被引用** | **41 个，84.1 MB** |
| 首页首次传输（修前） | 3,585 KB |
| 首页首次传输（修后） | 759.6 KB |

- 单张最大的 `aaa-home-title-screen-v1.png` = **14.79 MB**，另有 `aaa-hero-character-v1.png`
  6.29 MB、`aaa-ui-home-reference-v1.png` 5.16 MB，三张都是设计稿，无任何代码引用。
- `professions/` 与 `professions-cn/` 下的职业立绘约 **55 MB**，同样无引用——疑似未完成的功能资产。
- 被引用的图片全部是 PNG，且**文件名不含内容哈希**，因此拿不到长期缓存，每次导航都要重新校验。
- 仓库里已有的 WebP 版本体积小 **31–76 倍**，逐像素比对 MAE 仅 **0.93–1.44**（肉眼不可辨）。

**已修：** 9 条 `path` 从 PNG 切到已有的哈希 WebP，用户可见图片体积 27.1 MB → **549 KB**，
并顺带拿回 `immutable` 长缓存。

**未修（需你决定）：** 84.1 MB 未引用资源未删除。它们是仓库体积与克隆时间的主因，
但 `professions*` 可能对应你正在做的功能，删了会丢。建议：确认无用的移出仓库或用 Git LFS；
三张 `aaa-*` 设计稿建议移到 `docs/` 或外部设计库。

### 2.2 字体层（已修复）

| 项目 | 修前 | 修后 |
|---|---|---|
| `@font-face` 数量 | 0 | 1 |
| `document.fonts.size` | 0 | 1（status = loaded） |
| 字体族写法 | 8 种 / 120 处内联 | 4 个令牌 / 0 处内联 |
| 品牌字形一致性 | 随操作系统变化 | 一致 |

- 源字体 23.6 MB → 子集 **201,984 B（197 KB）**，压缩比 0.8%。
- 子集字符集来自客户端源码扫描：**898 个不同汉字 + 95 ASCII = 993 码位**。
- 用 fontTools 校验字体 cmap 与字符集**完全一致**（993 = 993，缺失 0、多余 0）。
- `unicode-range` 精确声明这 993 个码位，而不是图省事写 `U+4E00-9FFF`：
  **字体声明拥有的码位若缺字形，浏览器不会回落系统字体，而是渲染空白/豆腐块**，
  用户动态输入的汉字会直接消失。这是本次最容易踩的坑。
- macOS 上原本用楷体的 7 条规则（`.home-hero h1`、`.topbar__title` 等）用
  `--font-serif-kai` 精确保留了原意，未错换成宋体。
- CJK 全宽等宽，9 个汉字在子集与 `sans-serif` 下宽度都是 160.0px，
  因此换字体**零布局位移**（几何回归：首页 +0、回望 -6、知识库 +7）。
- 许可证 SIL OFL 1.1，`OFL.txt` 随字体分发。

### 2.3 排印层（已修复）

| 项目 | 修前 | 修后 |
|---|---|---|
| 字号档位 | 51 | 10（内容 7 + 展示 3） |
| 8–11px 的字号声明 | 330 处 | 0 |
| 裸 px 字号 | 518 处 | 0 |
| 首屏 12px 以下文字元素 | 34 个 | 0 |
| 同一个 `.section-title h2` | 30/31/36/38px 四种 | 单档 |

- 内容阶梯 7 档 12/14/16/18/22/28/36；展示阶梯 3 档 56/72/`clamp(88px,8vw,116px)`。
- 展示阶梯单独成组，因为它们是**桌面与移动成对出现**的响应式意图（如 `.home-hero h1`
  桌面 116 / 移动 78），硬压成一档会破坏响应式设计。
- 表单控件统一 16px，修掉 iOS 聚焦自动放大页面的问题。

### 2.4 色彩层（部分修复）

| 项目 | 修前 | 修后 |
|---|---|---|
| 文字色 alpha < .55 | 69 处 | 0（装饰性元素除外） |
| 金色在纸面上的对比度 | 1.48:1（FAIL） | 令牌已备好，角色未换 |
| 游离于令牌之外的 hex | 33 个 | 33 个（未动） |
| 不同的 `rgba()` 字面量 | 277 个 | 277 个（未动） |

- 深底文字层级全部实测：`.92`=12.89:1、`.72`=8.25:1、`.58`=5.73:1、`.55`=5.29:1，
  `.55` 是绝对下限。
- 纸面文字层级（在 `#eeeae0` 上）：`#1b2528`=13.03、`#33403f`=8.98、`#4a5654`=6.36、
  `#5c6a6b`=4.69。低于 `#5c6a6b` 只能做装饰。
- **未做**：把 `--paper` 从「卡片」提升为「页面底」。这是收益最大的视觉改动，
  但会改变全站观感，需你确认方向。令牌 `--gold-on-paper #7d5a1c`（5.22:1）与
  `--gold-on-ink #e4bd70`（10.23:1）已定义好，采用率检查会一直提醒它们未被使用。

### 2.5 间距层（已修复）

| 项目 | 修前 | 修后 |
|---|---|---|
| 间距取值 | 71 | 12 |

- 刻度 `0/4/8/12/16/20/24/32/40/48/56/64`，只吸附 ≤64px 的组件级间距；
  `>64px` 的页面级布局常量（如 hero 的 `padding: 126px 88px 78px`）一律不动，
  `clamp()/calc()` 内部参数不动。
- 几何回归全部为收紧 -24 至 -96px，**零溢出、零撑破**。

### 2.6 布局层（未改）

- `/privacy` 上存在**三个互不相关的垂直轴**：`h1` 左边缘 58px、顶栏品牌 110px、
  正文块 290px。h1 与正文之间 232px 的跃迁让页面读起来是「散」的。
- `--gutter` / `--content-max` / `--inset` 三个对齐令牌已定义，**目前 0 引用**。
- 建议：用 `--gutter` 统一 `main` 与 `topbar` 的左基线，需要内缩的内容用 `--inset`。
  这是「成本最低、专业感提升最明显」的一项。

### 2.7 CSS 架构层（未改）

| 项目 | 实测 |
|---|---|
| `styles.css` | 191 KB / 1,676 条规则 / 22 个 `@media` |
| 断点 | **7 个**：700(×11) / 701 / 860 / 900 / 980 / 1040 / 1180 |
| `!important` | 35 处 / 16 条规则（其中 9 条在 `@media print`，合规） |
| 常规样式里的 `!important` | 7 条，含一条 `*, *::before, *::after` |
| 后代选择器 ≥3 层 | 292 条 |
| 设计令牌 | tokens.css 定义 44 个，**仅 16 个被引用（36%）** |

- `700` 与 `701` 同时存在，说明是补丁而不是设计。建议收敛到 3 个断点（700 / 1024 / 1280）。
- 1,676 条规则在同一全局作用域下服务 20+ 路由，改一处要担心另外 19 个页面。
  建议按路由拆文件并用 `@layer` 分层。
- 令牌采用率 36% 不是错误——那是「目标刻度已定义、规则尚未迁完」的正常中间状态，
  但 `design-lint.mjs` 现在会把它打印出来，避免悄悄闲置。加 `--strict` 可让未采用令牌变成阻断。

### 2.8 JS 架构层（未改）

| 项目 | 实测 |
|---|---|
| 模块数 | 14 个，合计 294,505 B |
| `pages/index.js` | 125 KB |
| `app.js` | 121 KB（两者占 84%） |
| 首屏 JS 请求 | 14 个，292 KB |
| 构建步骤 | 无（原生 ES Modules 源码直出） |

- 无构建步骤是优点：部署简单、无供应链风险、调试即源码。
- 代价是首屏 14 个请求、292 KB 未压缩传输，且 `index.js` / `app.js` 两个巨石
  承载了全部路由与状态机。建议按 `app.js` 里已有的模块边界拆目录，打包可暂缓。

### 2.9 服务端（已改一处）

- 一体化 Node 服务同时提供静态页面与 `/api/v1`，`apps/user_client/server.mjs`。
- 静态文件走白名单：仅 `apps/user_client/index.html`、`apps/user_client/src/**`、
  `assets/generated/source/**` 可公开访问。
- **本次补充**：`.woff2` / `.woff` 的 MIME，并把 `woff2?` 纳入 `immutable` 缓存白名单
  （原先字体与哈希 WebP 都拿不到长缓存）。

## 3. 优先级建议

按「收益 ÷ 成本」排序：

| 优先级 | 事项 | 预期收益 | 成本 |
|---|---|---|---|
| P0 | 清理 84.1 MB 未引用资源 | 仓库体积 -73%，克隆与部署显著变快 | 低（但需先确认哪些是废稿） |
| P0 | 对齐脊统一（`--gutter` / `--inset`） | 消除 232px 的不连续，专业感提升最明显 | 低 |
| P1 | 纸面角色反转 | 视觉层次重构，收益最大 | 中（改变全站观感，需定方向） |
| P1 | 断点 7 → 3 | 少 4 份要同步的样式 | 中 |
| P2 | CSS 按路由拆分 + `@layer` | 降低 20+ 路由的改动风险 | 中高 |
| P2 | `index.js` / `app.js` 拆模块 | 首屏 JS 与可维护性 | 中高 |
| P3 | 未采用令牌迁移 | 消除 33 个游离 hex、277 个 rgba 字面量 | 中（机械但量大） |
| P3 | 键盘 / 读屏审计 | 合规与可达性 | 中 |
